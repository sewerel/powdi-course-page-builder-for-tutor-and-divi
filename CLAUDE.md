# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A WordPress plugin that lets site builders lay out Tutor LMS course pages with the Divi Builder instead of Tutor's default course page template. No PHP dependency manager and no test suite; the only build step is scoped to the optional Divi 5 module subsystem (see below). It's a fresh port of a sibling plugin (`powdi-course-page-builder-for-learndash-and-divi`) built for LearnDash instead of Tutor LMS — the two are independent codebases with no shared code, just parallel implementations of the same idea for different LMS plugins.

The plugin does two things:
1. Suppresses Tutor LMS's own single-course template so a Divi-Builder-authored page layout can render instead (`Powdcotu_Plugin::load_single_course_template()`).
2. Lets the suppressed pieces be re-inserted manually — either as native Divi 5 Builder modules, or (Divi 4, or anywhere else shortcodes are accepted) via three shortcodes: `[powdcotu_course_infobar]`, `[powdcotu_course_action_button]`, and `[powdcotu_course_content]`. The shortcode handlers and the Divi 5 modules' server classes both call internal Tutor LMS functions/templates directly, so they only render anything when Tutor LMS is active and the current post is a course.

## Architecture

```
powdi-course-page-builder-for-tutor-and-divi.php   # thin bootstrap: header, POWDCOTU_VER/URL/PATH constants,
                                                      # require_once includes/class-powdcotu.php, Powdcotu_Plugin::instance()
includes/
  class-powdcotu.php   # Powdcotu_Plugin singleton — owns which hooks get registered and whether
                         # the Divi 5 module subsystem gets loaded
  shortcodes.php        # the three shortcode functions, self-registering (call add_shortcode() themselves)
divi5-tutor-modules/     # native Divi 5 Builder modules (see below)
assets/css/style.css     # enqueued only on the Tutor course post type, styles the shortcode wrapper output
```

`Powdcotu_Plugin` (flat class name, no PHP namespace — matches the plugin's zero-tooling convention) is instantiated once from the main file. Its constructor calls `includes()` (currently just `require_once`s `shortcodes.php`) then `add_hooks()`. Shortcodes deliberately stay outside the class and self-register: retiring Divi 4 shortcode support later is meant to be exactly two edits — delete `includes/shortcodes.php`, delete the one `require_once` line in `includes()` — without touching the class itself.

`Powdcotu_Plugin::load_single_course_template()` hooks `template_include` at priority **100**, one above Tutor core's own `TUTOR\Template::load_single_course_template` (priority 99 on the course post type), so this plugin's filter wins and hands the theme's normal single-post template back to WordPress (via `get_single_template()`) so a Divi-built page layout renders instead. It bails early on `?subpage=` requests so Tutor's own learning-area (lesson player/dashboard) template is left untouched.

### Divi 5 native modules (`divi5-tutor-modules/`)

Ported from the sibling theme `divi-tutor-theme`'s own `divi5-tutor-modules/` subsystem: `DTUTCourseButtons`, `DTUTCourseContent`, `DTUTCoursePrice`, and `DTUTCourseStatus` (the theme's 5th module, `DTUTCourseGrid`, was intentionally left out — it's a multi-course archive/listing module, outside this plugin's single-course-page scope). Structure mirrors the theme's:
- `visual-builder/src/modules/{Module}/` — JS/JSX/CSS source (block metadata in `module.json`, entry `index.jsx`, server-shared settings/render files). **Copied from the theme, with the `d4Shortcode` key and `conversion-outline.json` dropped** (this plugin ships no Divi 4 module counterpart — Divi 4 users keep the shortcodes — so a Divi5→Divi4 conversion outline pointing nowhere would be dead/misleading) and the ajax action string renamed to this plugin's own convention (see below). Otherwise untouched — block names (`divi-tutor/buttons` etc.) and other string literals are the theme's own, so do not rename anything under here without also re-checking the matching `server/*.php` file.
- `server/{Module}.php` — PHP module registration (`ET\Builder\...\ModuleRegistration`), namespace `Powdcotu\Divi5Modules\Server`. Class **basenames** (`DTUTCourseButtons`, `DTUTCourseContent`, `DTUTCoursePrice`, `DTUTCourseStatus`) must stay exactly as-is: `server/Ajax.php`'s `handle_ajax()` dynamically resolves `__NAMESPACE__ . '\\' . $context`, where `$context` is a literal string sent by the matching module's `ajax.jsx`. Each `get_content()` calls Tutor core functions/templates directly, near-verbatim from the theme (an intentional duplication of `includes/shortcodes.php`'s own rendering logic, not a shared helper — matches how the LearnDash sibling plugin ported its own modules). Unlike the theme's version, these files no longer self-register via their own `add_action('divi_module_library_modules_dependency_tree', ...)` block at the bottom — see the Loader note below for why.
- `partials/` — plugin-local copies of the theme's render partials (`course-buttons.php`, `course-content.php`, plus the three `divi5_button-{tutor,edd,woocommerce}.php` monetization sub-partials), referenced via `POWDCOTU_PATH . 'divi5-tutor-modules/partials/...'` from the server classes. The theme's own login-modal helper wasn't ported; `course-buttons.php` instead hooks `wp_footer` to load Tutor core's own `views/modal/login.php` directly (`tutor_load_template_from_custom_path()`), consistent with this plugin's existing habit of calling straight into Tutor core rather than duplicating its markup.
- `build/{Module}.js` — compiled output, committed to the repo (WP.org SVN doesn't run builds). None of these 4 modules produce a per-module stylesheet (all styling goes through Divi's own decoration options), so there's no `styles/` directory here — unlike the theme, which ships one for the excluded `DTUTCourseGrid` module.
- `divi5-tutor-modules.php` — the `Powdcotu\Divi5Modules\Loader` singleton. Its constructor only registers the `wp_enqueue_scripts`/`divi_visual_builder_assets_before_enqueue_scripts` hooks; the actual module registration lives in `register_dependencies($dependency_tree)`, which requires each `server/{Module}.php` and calls `$dependency_tree->add_dependency(new $class())` **directly** (no nested `add_action()` — see below for why), guarded by `interface_exists('ET\\Builder\\Framework\\DependencyManagement\\Interfaces\\DependencyInterface')` (this plugin isn't a Divi child theme, so unlike the theme it can't assume Divi's install path — it defers to Divi's own autoloader instead, which is guaranteed registered by the time `register_dependencies()` runs, see below).
- Ajax wiring uses this plugin's own names, not the theme's: action `wp_ajax_powdcotu_divi5_module_action`, nonce `powdcotu_divi5_module_nonce` (the theme's originals were `divi_tutor_module_action`/`divi_tutor_module_nonce`).
- **Registration hook is `divi_module_library_modules_dependency_tree`, not `init`** — this was a real bug caught and fixed during development (confirmed with `error_log()` timing traces against a live Divi 5 request before landing the fix): Divi 5's `et_setup_builder_5()` (`init` priority 0) requires `Packages/ModuleLibrary/Modules.php`, whose top-level code both fires `do_action('divi_module_library_modules_dependency_tree', $dependency_tree)` *and*, immediately after, calls `DependencyTree::load_dependencies()` (which is what invokes each dependency's `->load()`) — all synchronously, still within that same priority-0 callback. A plugin hook registered on `init` at *any* priority (even 0, even a callback added from within another priority-0 callback on a *different* action) runs too late, because by then that one-off `do_action()` call has already returned and the dependency list is already closed off — this is why the theme's original nested-`add_action` pattern (each server file self-registering `add_action('divi_module_library_modules_dependency_tree', ...)` only once `include_d5_modules()` was reached via an `init`-hooked loader) silently never fired, and it's also why `Powdcopa_Plugin::maybe_load_divi5_modules()` in the LearnDash sibling plugin — which uses that exact same `init`-gated pattern — is suspected to have the identical bug. `Powdcotu_Plugin::add_hooks()` instead registers `maybe_register_divi5_modules()` directly on `divi_module_library_modules_dependency_tree` (Divi's own documented "hook for adding modules from 3PS extension") at plugin-construct time — i.e. long before `init` — so the callback is always in place before Divi's one-shot `do_action()` fires. It's still safe to check `DIVI_TUT_VER`/`ET_CORE_VERSION`/Divi's autoloader *inside* that callback (rather than at registration time), because the callback itself doesn't actually execute until Divi fires the hook — by which point the active theme's `functions.php` (and Divi's own autoloader) have already run regardless of how early we registered for it.
- Own self-contained npm/webpack toolchain (`divi5-tutor-modules/package.json`, `webpack.config.js`, gitignored `node_modules/`), separate from the plugin root's `package.json` (release-tooling only). After editing anything under `visual-builder/src/modules/`, rebuild with `npm run build:win` (or `npm run build` on non-Windows) from inside `divi5-tutor-modules/` and commit the resulting `build/*.js`.
- No Divi 4 counterpart exists for these 4 modules (Divi 4 users keep using the shortcodes) — don't add one speculatively.

## Working in this codebase

- No PHP autoloader anywhere: every file is pulled in via explicit `require_once`. `Powdcotu_Plugin` and the Divi 5 `Loader`/server classes are each guarded (`class_exists()` / `interface_exists()` checks) rather than relying on include-once semantics alone.
- Because the shortcode handlers and the Divi 5 server classes' `get_content()` methods call internal Tutor LMS functions/templates directly (not through a documented public API), a Tutor LMS core update can change those file paths/function signatures/hook priorities — when editing, re-check the equivalent logic in the active Tutor version's `templates/single/course/course-entry-box.php`, `templates/single/course/course-topics.php`, and `classes/Template.php`.
- A recurring implementation detail worth knowing before touching `course-entry-box.php`/`course-topics.php` integration: both Tutor templates read `global $is_enrolled;` as their first statement. `tutor_load_template()`'s own `extract($variables, EXTR_SKIP)` happens in a different scope and is irrelevant here — `$is_enrolled` must be set as a true PHP global by the calling shortcode *before* calling `tutor_load_template()`, not passed via the `$variables` array.
- The `Prefix: powdcotu` plugin header and the `powdcotu_`/`Powdcotu` function/class/hook prefix are this project's naming convention — keep any new functions/shortcodes/hooks under that prefix. Known, deliberately-justified exceptions: the `global $is_enrolled` variable (must match Tutor core's own global) in `includes/shortcodes.php`, the `apply_filters('tutor_alter_enroll_status', ...)`/`apply_filters('tutor_course_sell_by', ...)` calls (invoking Tutor core's existing filters, not defining new ones), and the `Powdcotu\Divi5Modules` namespace plus `DTUT*` class basenames inside `divi5-tutor-modules/` (needed because that subsystem is a near-verbatim port of the theme's own namespaced code).
- `ready.js`'s zip-ignore list uses a bare `'*.json'` pattern, which (verified) only strips root-level JSON files, not nested ones — the Divi 5 modules' `module.json`/`defaultAttrs.json` (read directly off disk at runtime by `ModuleRegistration::register_module()`) do survive packaging; `**/package.json`, `**/package-lock.json`, `**/webpack.config.js`, and `**/*.jsx` are separately ignored so the npm/webpack dev tooling under `divi5-tutor-modules/` doesn't ship. Re-verify this with a real `node ready.js` + unzip if that ignore list is ever changed.
- This plugin was checked against the official WordPress.org [Plugin Check](https://wordpress.org/plugins/plugin-check/) tool (`wp plugin check <slug>` via WP-CLI) with zero errors and only two expected/cosmetic warnings remaining as of v1.1.0 (`.gitignore` "hidden file" and `CLAUDE.md` "unexpected markdown file" — both already excluded from the shipped zip by `ready.js`, present in the LearnDash sibling plugin too). Re-run it after any change that touches superglobals, hook/variable naming, or `readme.txt` headers, before assuming the change is WP.org-submission-ready. On this repo's dev machine, WP-CLI isn't on `PATH` as bare `wp` from a Bash session — invoke it as `"D:/laragon/bin/wp-cli/wp.bat" --path="D:/projects/tutor" plugin check powdi-course-page-builder-for-tutor-and-divi`.
- Known, deliberately-justified PHPCS suppressions from that scan (don't "fix" these by renaming/rewriting unless the underlying code changes): `phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped` on the two `et_core_esc_previously()` calls that output already-`tutor_kses_html()`-sanitized HTML (re-escaping with `esc_html()` there would break the markup — the one exception, `course-content.php`'s lesson-duration output, IS plain text and uses `esc_html()` directly instead, no ignore needed); `phpcs:ignore WordPress.Security.ValidatedSanitizedInput.MissingUnslash` on `Ajax.php`'s `$_POST['context']` (immediately checked against the `$allowed` whitelist, so skipping `wp_unslash()` is harmless — the other two ajax context/label reads, in `DTUTCourseButtons.php`/`DTUTCoursePrice.php`, aren't whitelisted the same way and do call `wp_unslash()`); and a `phpcs:disable WordPress.NamingConventions.PrefixAllGlobals.NonPrefixedVariableFound` at the top of each of the 5 `partials/*.php` templates, since their local variable names intentionally match the corresponding Tutor core template's own names for diffability.
- There is no automated test suite. Changes are verified by activating the plugin on a real WordPress + Tutor LMS + Divi install (this repo's dev install lives at `D:\projects\tutor`) and checking a course page, both logged out and as an enrolled user (both the shortcodes and, on Divi 5, the native modules in the Visual Builder).

## Release tooling (Node scripts, dev-only — not part of the plugin runtime)

- `node ready.js` — packages the plugin into a zip (via `archiver`) at `D:/plugins/<dirname>.zip`, excluding `node_modules` (anywhere in the tree), the release scripts themselves, `.git`, root-level JSON files, nested `package.json`/`package-lock.json`/`webpack.config.js`, and `.jsx` files; also copies `changelog.txt` to `D:/plugins/changelog-<dirname>-v<version>.txt`, with the version read from the `Version:` header in the main plugin PHP file. Writes outside the repo to a hardcoded `D:/plugins` path — only meaningful on the original maintainer's machine.
- `node trunk.js` — copies the plugin (minus dev tooling files) into a local WordPress.org SVN trunk working copy at a hardcoded `D:/wporg/<dirname>/trunk` path.
- **`bump.js` is not present in this repo** (unlike the sibling LearnDash plugin, which has one). `changelog.txt` exists and follows the same format `bump.js` produces elsewhere in this maintainer's projects (`## [version] – date` header, `### 🚀 New Features`/`### 🛠 Improvements`/`### 🐛 Bug Fixes` sections, `- ` bullets) — until `bump.js` is added here, version bumps in the plugin header (both the `Version:` doc-block line and the `POWDCOTU_VER` constant — kept in sync by hand) and new changelog entries need to be done by hand.

`readme.txt` follows the standard WordPress.org plugin readme format (`=== Header ===`, `== Description ==`, etc.) and should stay in sync with the plugin header in the main PHP file (version, tested-up-to, description, shortcode/module list) when any of those change.
